# E3. Swap the linear solver — nine Tier 1 entries

Exercise, from the brief: replace the sparse in-place LU used in the Rosenbrock
stages by another solver (a dense LU, or an external library's sparse solver),
chosen at run time, without editing the integrator. For each entry: is there a
linear-solver interface, what does it receive, how many call sites does the
integrator have, does the TS1 benchmark's path go through the interface, do the
generated Jacobian kernels or the species ordering assume the current storage,
and what would the tests check.

Method: read-only, from each entry's final commit at
`~/NSF-NCAR/tier1-work/verify/<run>/clang/<run>/`, following the benchmark
driver into the library. Line numbers are `path:start-end` in that tree. The
yardstick is MICM: its Rosenbrock takes the linear solver as a template policy
(`include/micm/solver/rosenbrock.hpp:49-57`), calls `linear_solver_.Factor`
once per step attempt (`rosenbrock.inl:342`) and `linear_solver_.Solve` once per
stage (`rosenbrock.inl:188`), plus three sites in constraint initialization
(`rosenbrock.inl:592,603,702`); the policy is chosen when the solver is built
(`solver_builder.hpp:268-299`), not at run time.

"Edit sites" counts the distinct places that must change to run TS1 with
another solver; the new solver's own factor and solve functions are new code and
are not counted. In every entry the matrix a solver receives is the shifted
negative Jacobian, `alpha*M - J`, in the entry's own storage.

## sol-high

**Edit sites (1).** `src/bench.c:183-184`: after `chem_state_create`, call
`chem_set_linear_solver(groups[g].state, (ChemLinearSolver){factor, solve})`.
Nothing in the library changes; the integrator (`src/rosenbrock.c:28-131`)
calls `s->linear.factor` and `s->linear.solve` only.

**Extension point.** `typedef struct { ChemStatus (*factor)(const ChemMechanism *,
size_t cells, double *matrix); void (*solve)(const ChemMechanism *, size_t cells,
const double *matrix, double *rhs); } ChemLinearSolver` (`include/chem.h:95-98`);
`chem_set_linear_solver(ChemState *, ChemLinearSolver)` (`include/chem.h:209`,
`src/linear.c:181-186`, rejects a NULL member); stored per state in
`ChemState.linear` (`src/internal.h:29`), default `chem_linear_mozart()` at
state creation (`src/state.c:20`), copied by clone (`src/state.c:65`);
constructors `chem_linear_mozart`/`chem_linear_doolittle` (`src/linear.c:91-92`).

**What it receives.** `factor(mechanism, cells, matrix)`, `solve(mechanism,
cells, matrix, rhs)`: `matrix` is the packed Jacobian, `nnz * cells` doubles,
element-major with the group's cells contiguous (`src/linear.c:11-24` indexes
`matrix + slot * nc`); `rhs` is `species * cells`. `ChemMechanism` is opaque
(`include/chem.h:41`; struct in `src/internal.h:9-23`), so a backend maps
(row, column) to a slot through `chem_jacobian_size` and
`chem_jacobian_index(mechanism, row, column)` (`include/chem.h:146,192`). No
context pointer; the group width is the `cells` argument. `factor` returns
`ChemStatus` (CHEM_SINGULAR is honoured, `src/rosenbrock.c:58-60`); `solve`
returns void.

**Call sites.** Rosenbrock: factor `src/rosenbrock.c:58`, stage solve
`src/rosenbrock.c:82` (inside the stage loop `:61-84`). Backward Euler:
`src/backward_euler.c:44,48`. Constraint initialization:
`src/constraints.c:140,143,163`. All seven go through `s->linear`.

**TS1 path.** `src/bench.c:176` creates the mechanism, `:181-185` one state per
group, `:187` the three-stage parameters, `:194` and `:202` `chem_solve`, which
runs `integrate` and so the state's `linear` pair. The driver never calls
`chem_set_linear_solver`, so TS1 uses the Mozart default.

**Storage assumptions.** The Jacobian assembly writes through `m->index` and
`m->diagonal` (`src/process.c:69,73,80`), the packed slots built with symbolic
fill for the unpivoted elimination (`src/mechanism.c:104-127`); the elimination
triples (`src/mechanism.c:129-145`) serve only the built-in factor. The species
order is the generated data's (Markowitz in `tools/configure.py`, README.md:89-90),
fixed before the C library sees it. A replacement consumes the same packed
matrix; nothing generated changes. The matrix handed to `solve` is whatever
`factor` left in `s->jacobian` (in place); an out-of-place backend keeps its
factors elsewhere and ignores it.

**Documentation.** DESIGN.md:138-142 describes exactly this ("pass a
`ChemLinearSolver` to `chem_set_linear_solver`. The factor callback receives
the sparse matrix storage and cell count; solve overwrites its right-hand side.
The public index API maps rows/columns into that storage"); matches the code.

**Tests.** `tests/test_solvers.py:120-132` runs the stiff five-species case with
`chem_linear_mozart()` and `chem_linear_doolittle()` installed by
`chem_set_linear_solver` and requires identical step statistics;
`tests/test_linear.py:76-112` factors and solves packed random, dense and
diagonal matrices through a `ChemLinearSolver`'s `factor`/`solve` (in place and
separate L/U); `tests/test_stiff_analytical.py:66,83,98,117`,
`tests/test_analytical.py:65` and `tests/test_aerosol.py:132` repeat analytical
and aerosol cases per algorithm. A new backend would join those loops (from
Python it needs a C constructor like `chem_linear_mozart`) and would be checked
for agreement with the default and for its `decompositions`/`solves` counts.

**Patch sketch.**
```
/* dense_lu.c (new) */
static ChemStatus dense_factor(const ChemMechanism *m, size_t nc, double *a)
{ /* gather a[chem_jacobian_index(m,i,j)*nc+c] into an n*n*nc buffer, LU it */ }
static void dense_solve(const ChemMechanism *m, size_t nc, const double *a, double *x)
{ /* forward/back substitution on the buffer; a is ignored */ }
/* src/bench.c:183-184 */
     status = chem_state_create(m, groups[g].cells, &groups[g].state);
+    if (status == CHEM_OK && use_dense)
+        status = chem_set_linear_solver(groups[g].state,
+                                        (ChemLinearSolver){dense_factor, dense_solve});
```
The dense buffer must be static or `_Thread_local`: the callbacks carry no
context and `ChemState` is opaque.

**Ease: 4.** One call through a documented, tested run-time hook, but the hook
has no context pointer, so an external library's handle and workspace cannot
travel with the state, and `solve` cannot report failure.

defaults.

**Storage assumptions.** The generated Jacobian kernel writes `out[<literal

order and fill (`tools/configure.py:118-133,148-158,171-181`), and the loader

lists (`src/model.c:262-298`). A replacement solver reads the same packed
matrix, so the kernels stand; only a change of the Jacobian's own storage would
force regeneration (the kernels have literal slots and ignore `model`,
`tools/configure.py:186-190`).

**Documentation.** DESIGN.md:31 ("receives a parameter table, a step-size
controller function, and factor/solve function pointers") and :35 ("A new

## Cross-entry notes

- Every Sol and Astra entry gives the backend the same object: the packed,
  element-major `nnz * cells` block of the shifted negative Jacobian, with the
  symbolic fill of MICM's unpivoted elimination already in the pattern and the
  species in diagonal Markowitz order. A dense LU or an external sparse solver
  converts from that layout inside the callback; the generated or precomputed
  Jacobian kernels are unaffected, because they target the Jacobian's storage,
  not the solver's. Only a design that let the solver own the Jacobian's layout
  would reach into the generators (`sol-max tools/configure.py:171-181`,
  `astra-xhigh tools/generate.py:94-99`).
- luna-max's callback differs in kind: per cell, out of place, and it must
  apply `alpha` and the mass diagonal itself; this is MICM's non-in-place
  `LinearSolver` shape rather than `LinearSolverInPlace`.
- In all seven hook entries the integrator's call sites are the same as MICM's
  (one factor per attempt, one solve per stage, three in constraint
  initialization), and backward Euler goes through the same hook except in
  sol-max (its own `ChemEuler` pair) and luna-max (dense routines).
- A test of the form "install a counting or alternative backend, compare step
  statistics and results with the default" exists in sol-high
  (`tests/test_solvers.py:120-132`), sol-xhigh (`tests/test_integrators.c:167-199`),
  sol-max (`tests/solver_cases.py:70-83`), astra-high
  (`tests/test_rosenbrock.c:88-115`), astra-xhigh (`tests/test_solver_core.c:65-104`),
  astra-max (`tests/native_cases.c:31-65`) and luna-max
  (`tests/test_cpu.c:2165-2290`); luna-xhigh compares its two enum values
  (`tests/test_rosenbrock_utilities.c:116-135`); luna-high has nothing to
  install.
