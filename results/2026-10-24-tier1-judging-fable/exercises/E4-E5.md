# E4 (add a rate-constant type) and E5 (use another mechanism), nine Tier 1 entries

Read-only paper exercises on `~/NSF-NCAR/tier1-work/verify/<run>/clang/<run>/`
(paths below are relative to an entry's root). MICM e15898ce at this commit has no
configuration reader of its own (`find include -iname '*config*'` and a grep for
`camp-data` under `include/` and `src/` return nothing): the "MICM format" is the
CAMP YAML/JSON of `test/tutorial/configs/`, which MICM's tutorials rebuild by hand
with explicit unit conversions (`test_rate_constants_no_user_defined_by_hand.cpp:13,
85, 105-108`: `MOLES_M3_TO_MOLECULES_CM3 = 1e-6 * AVOGADRO`; Troe `k0_A` × factor², `kinf_A`
× factor for the two-reactant Troe; ternary `kinf_A` ÷ factor for the one-reactant
ternary). That convention, generalized by reaction order, is the yardstick used here.

The new type for E4: `k = A·exp(C/T)·(T/300)^B·(1 + D·P/101325)`, configuration type
`PRESSURE_ARRHENIUS`, fields `A, B, C, D` (D is a pressure coefficient, default 0, so it
cannot share the Arrhenius `D` slot whose default is 300), unit rule `A × f^(order−1)`.

## E4 summary

Ease: 5 one place through a run-time hook; 4 a few edits in one module and no hidden
coupling; 3 several files or a hidden limit/coupling; 2 invasive; 1 restructuring.
"Sites" counts distinct places that must change, tests excluded. Every entry keeps rate
types in both Python (type table + unit rule) and C (enum + evaluator), so 4 is the
ceiling for a configurable type; ratings below 4 record a hidden coupling beyond that.

In every entry the TS1 benchmark takes the same rate path as the generic API: TS1's
rate constants come from the committed JSON through the reader/generator (a translator
of `ts1_mechanism.hpp` produces that JSON once, offline), and the per-cell evaluator is
the one switch statement listed below. The two kernel generators (sol-max,
astra-xhigh) emit forcing/Jacobian kernels that only read the precomputed rate array,
so no generated code changes for a new rate type. No entry has a configuration type
that maps to its callback rate, so the callback serves C-built mechanisms only.

## Consistency check of the ratings

E4: the irreducible change in every entry is one Python type table, one Python unit
rule, one C enumerator and one C evaluator case. astra-high and luna-max need nothing
beyond that in three files (reader, header, evaluator) and get 4. The other seven
each add at least one of: a positional table indexed by enum value (sol-high
`rate_family[]`, sol-xhigh `rate_priority[]`, astra-max `inspect.c type_order[]`,
astra-xhigh `chem_rate_type_order`), an ordinal or parallel-list coupling across the
language boundary (astra-max integer codes, sol-max `KINDS`/`C_KINDS` and the double
sort), an exhausted or shared parameter layout (luna-xhigh's 24 slots and shared
defaults, sol-xhigh's one flat field set), or logic in two files on one side
(luna-high's reader/generator split and two C evaluators); they get 3. No entry needs
generated kernels changed (2) or restructuring (1).

E5: the six sol/astra entries share one profile: a documented command, one Makefile
rule, a symbol chosen by option, order-dependent unit conversion, consistent species
indices, and tests that run the generator on three tutorials against hand-built
mechanisms; they get 4 (not 5: a new mechanism is a generate-compile-link cycle, not a
run-time hook). luna-max and luna-xhigh are as easy to drive (no Makefile edit) but
their readers mis-convert rate coefficients for any reaction order other than the
tutorial's; they get 3. luna-high additionally emits wrong reactions whenever its
Markowitz order differs from the input order, with a two-step undocumented pipeline
and no Makefile rule; it gets 2.
