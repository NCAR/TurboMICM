# E4 and E5 across the nine Tier 1 entries

Worked on paper from each entry's final commit, read-only, at
`~/NSF-NCAR/tier1-work/verify/<run>/clang/<run>/`. Citations are
`path:line` from that root. For E5, copies of each entry's reader and generator
were run in scratch on small configurations (section E5.0). Nothing was built or
run inside an entry.

The new type is called `PRESSURE_ARRHENIUS` throughout, with configuration keys
A, B, C, D:

k = A·exp(C/T)·(T/300)^B·(1 + D·P/101325)

## Rating rules applied to all nine

**E4.** 4: only the type-dispatch edits the design exposes (a reader table entry
or branch and its unit rule in Python; the enum, parameter storage, defaults and
evaluator in C), with no second evaluation path, no table indexed by the enum, no
bound tied to one particular enumerator, and no Python list or test that mirrors
enum integers or struct layout. 3: the same plus at least one such hidden
coupling. 2 would need the TS1 path or generated kernels to change; no entry is
that bad. No entry lets a configuration declare a callback rate, so none gets 5.

**E5.** 4: regenerate under the benchmark's symbol (or repoint one Makefile rule)
and link, through the generic library path, with the generator tested on
non-TS1 configurations by species name, and no wrong-result defect found. 3: the
same effort, plus a hidden coupling that decides correctness (generated kernels
that depend on Python copies of C logic), or a unit convention for host-supplied
rates that differs from MICM's tutorials. 2: the reader must be fixed before
another MICM-format mechanism gives correct results.

## E4, common to all nine

- MICM's Arrhenius is A·exp(C/T)·(T/D)^B·(1 + E·P)
  (`micm/include/micm/process/rate_constant/rate_constant_functions.hpp:60-65`).
  The new type equals it with D_Arrhenius = 300 and E = D/101325. Every
  entry's reader passes E for ARRHENIUS, so a reader-only alias (one Python
  edit) would serve in all nine, differing by at most an ulp or so from
  evaluating D·P/101325. It is not counted as the end-to-end change.
- Every entry has a callback rate type for mechanisms built in C. No reader
  accepts one from a configuration, so a callback cannot replace a configured
  type in any entry.
- The kernels that sol-max and astra-xhigh generate read rate constants computed
  by the library, so neither kernel emitter changes. In sol-max the reader's
  type order must still agree with the C enum (below).

# Defects found, and confidence

1. **luna-max, luna-xhigh, luna-high: wrong rate constants for MICM-format
   mechanisms.**
   - The readers convert CAMP coefficients with fixed exponents (Troe k0 × conv²,
     kinf × conv; ternary kinf ÷ conv), regardless of reaction order. They never
     convert Arrhenius, tunneling, branched, Taylor or JPL19 coefficients
     (`luna-max/tools/generate_c.py:88-94`, `luna-xhigh/tools/generate.py:127-136`,
     `luna-high/tools/read_config.py:75-79`).
   - Any reaction whose order differs from the tutorial's gets a rate constant
     wrong by powers of 6.02e17. Examples: a bimolecular Arrhenius (unconverted;
     should be × 6.02e17), a termolecular Arrhenius with M (should be
     × 3.6e35), a one-reactant Troe.
   - **Confidence: high.** The scratch runs show it directly, the six Sol and
     Astra readers agree with each other on the order-dependent values, and MICM
     itself converts a bimolecular Arrhenius A by MOLES_M3_TO_MOLECULES_CM3
     (`micm/test/regression/regression_policy.hpp:143`). The tutorials pass only
     because their reaction orders match the fixed exponents. TS1 is unaffected.
2. **luna-high: reactions name the wrong species.**
   - The known index defect is confirmed: generated terms carry their input-order
     index beside a species table in Markowitz order with third bodies last.
   - **Confidence: high**, from both the code and the scratch output. It is
     invisible to the entry's tests, because the tutorials' order is the identity
     and TS1's JSON has no indices.
3. **sol-xhigh: user-defined rate scaling.**
   - For molecule cm-3 input, the reader multiplies the scaling of photolysis,
     emission, loss and user-defined reactions by conv^(n−1)
     (`tools/configure.py:149-150`). MICM's Robertson configuration, run with
     MICM's tutorial values (r2 = 3e7, r3 = 1e4), therefore gets rate constants
     6.0e17 times too large, and emissions are scaled by 1/6.0e17.
   - **Confidence: medium-high that this departs from MICM's semantics.** The
     entry chose it deliberately (`DECISIONS.md:17-19`) and its own test feeds
     the configured mechanism compensated values
     (`tests/test_configuration.c:27-37`). The other eight emit a scaling of 1.

Latent hazards, not current defects (confidence high on the mechanism of each):

- **astra-max:** following `DESIGN.md:186`'s "append an enum value" with the
  matching `RATE_NAMES` append makes the new type evaluate as `CH_LAMBDA`, with
  NaN rates.
- **astra-high:** a type added after `CHEM_CALLBACK` is scanned by
  `chem_set_rate_callback` (`src/mechanism.c:146`).
- **sol-max and astra-xhigh:** the generated kernels are correct only while the
  Python copies of C's ordering, fill and type sort agree with C. They agreed on
  every configuration tried here and in the entries' own tests.
