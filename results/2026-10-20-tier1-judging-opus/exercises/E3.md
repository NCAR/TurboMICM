# E3. Swap the linear solver

Exercise: replace the sparse in-place LU used in the Rosenbrock stages by another
solver (a dense LU, or an external library's sparse solver), chosen at run time,
without editing the integrator, such that the TS1 benchmark's integrator uses it.
Worked on paper from each entry's final commit
(`~/NSF-NCAR/tier1-work/verify/<run>/clang/<run>/`). Paths below
are relative to that root.

Two remarks apply to all nine:

- **No benchmark has a linear-solver option.** In every entry the benchmark
  must be edited to parse a choice and install the new solver; the counts below
  include those edits.
- **An external sparse library is outside the Tier 1 rules** (ISO C11, libm and
  OpenMP only), so the in-rules case is a dense LU written in C. Both cases need
  the same things from the interface: somewhere to keep the factors between the
  factorization and the stage solves, and access to the sparsity pattern.

MICM, for comparison: the linear solver is a compile-time `LinearSolverPolicy`
template argument (`include/micm/solver/rosenbrock.hpp:49`). The integrator
calls `Factor` once per attempt, after `AlphaMinusJacobian`
(`include/micm/solver/rosenbrock.inl:330-349`), and `Solve` once per stage
(`rosenbrock.inl:186-193`).

Sizes for TS1, used in the hazards below: there are 209 variables (210 species
minus M; luna-high keeps M as a 210th row), and 2,359 packed entries after fill
in sol-max's Markowitz order (`if (m->nnz != 2359)` in sol-max's build output
`generated/ts1.c:20558`; other entries' orders give similar counts). A dense matrix has 209² = 43,681 entries per cell,
about 349 KB, against 19 KB for the packed storage. Keeping dense factors for
every cell of a 32-cell group takes 11 MB; for all 10,000 cells it takes 3.5 GB.

In all nine, the Jacobian is assembled in the LU's own storage format and
index form, at offsets fixed by the current pattern. In seven it is assembled
directly into the array that is factored in place. In luna-max and luna-high it
goes into a separate array of the same form, which is copied before the
factorization. A solver that needs another input storage must convert inside
its factor call, or the assembly must change. That assembly is generated code
in sol-max and astra-xhigh, and precomputed index lists or maps in the other
seven.

## Per-entry details

### sol-high

- **TS1 path.** `main` creates one state per group (`src/bench.c:181-185`), and
  each state gets `s->linear = chem_linear_mozart()` (`src/state.c:20`). Solves go
  through `chem_solve`, then `integrate` (`src/rosenbrock.c:133-138,28-131`).
  The integrator has one factor call (`:58`) and one solve call per stage
  (`:82`). After a rejection it rebuilds the Jacobian because the
  factorization overwrote it (`:122`). The same pointers serve backward Euler
  (`src/backward_euler.c:44,48`) and constraint initialization
  (`src/constraints.c:140,143,163`).
- **Extension point.** `ChemLinearSolver {factor, solve}`
  (`include/chem.h:95-98`), stored per state (`src/internal.h:29`), set by
  `chem_set_linear_solver`, which rejects NULL members (`src/linear.c:181-186`),
  and copied by `chem_state_clone` (`src/state.c:65`). Constructors:
  `chem_linear_mozart/doolittle` (`src/linear.c:91-92`).
- **Handed to the solver.** See the table above. `ChemMechanism` is opaque in
  the public header, but code inside the library can include `internal.h`. The
  right-hand side is species-major, `k[i*cells+c]`.
- **Jacobian assembly.** Precomputed jobs of (reaction, independent,
  skipped) (`src/mechanism.c:150-159`) write through `m->index` and
  `m->diagonal` into the packed array (`src/process.c:47-100`). The generator
  emits data only (`tools/configure.py:216-246`).
- **Edit sites (4).**
  1. `src/linear.c:91-92`: add a dense factor (solve can reuse
     `chem_linear_solve`) and `chem_linear_dense()`. Alternatively put it in a
     new file and add it to `Makefile:43` `LIBSRC`.
  2. `include/chem.h:198-199`: declaration.
  3. `src/bench.c:153-161`: `--linear` option.
  4. `src/bench.c:181-185`: `chem_set_linear_solver(groups[g].state, …)`.

  The integrator needs no edit.
- **Hazards.**
  - Hidden limit: there is no context pointer, so `solve` receives only the
    `nnz × cells` array that `factor` left behind. An unpivoted dense LU works,
    because its factors fall inside the no-pivot fill pattern and can be
    gathered back into the packed array. A pivoted LU, separate L and U, or a
    library's numeric object needs static or `_Thread_local` storage or a
    per-call allocation.
  - The library's own separate-factor API, `chem_factor_separate` with L and U
    buffers (`src/linear.c:94-120`), cannot be installed through this hook for
    the same reason. It also assumes the passed `factor` leaves packed L\U in
    the pattern.
  - Installing the pair changes backward Euler and constraint initialization
    too, since they use the same pointers.
- **Tests.**
  - Existing coverage uses only the two built-ins:
    - `tests/test_linear.py:76-120,163-168` runs MICM's LU fixtures through the
      pair's pointers. The in-place cases rebuild L and U from the packed array
      (`:88-92`), which only works for a solver that leaves L\U in the pattern.
    - `tests/test_analytical.py:65`, `tests/test_stiff_analytical.py:66` and
      `tests/test_aerosol.py:132` integrate after `chem_set_linear_solver`.
    - `tests/test_solvers.py:120-131` compares Mozart and Doolittle step counts
      across rejections.
  - A new solver needs: a ctypes binding (`tests/chemffi.py:117-118`), `'dense'`
    added to `tests/test_linear.py:163`, analytical variants, and the TS1
    100-cell gate with the new flag.
  - Missing today: no test counts hook invocations, and nothing runs the
    benchmark with a non-default solver.
- **Documentation.** `DESIGN.md:138-142` says to pass a `ChemLinearSolver` to
  `chem_set_linear_solver`, that the factor receives the sparse storage and cell
  count, and that the public index API maps rows and columns to storage. This
  matches the code. It does not say that the factors must fit in that storage.
- **Patch sketch.**

## Consistency and order

The nine ratings fall into five kinds of change. Every kind also needs the
benchmark edit, so that edit does not separate them.

| Kind | Entries | Rating |
|---|---|:-:|
| Hook with a per-group or per-state context and a status return | astra-high, astra-xhigh, astra-max | 5 |
| Hook with one context shared by all threads (and, in luna-max, by the controller) | sol-xhigh, luna-max | 4 |
| Hook with no context, so the factors must fit in the packed `nnz × cells` matrix (a hidden limit) | sol-high, sol-max | 3 |
| Integrator edit needed: an enum chooses between static functions inside the TS1 integrator | luna-xhigh | 2 |
| Integrator edit needed: no selector; static functions called from two paths | luna-high | 2 |

What the context means in practice:

- With a per-group context, any solver works, including a pivoted LU or a
  library handle.
- With a shared context, the same solvers work if the context keeps one slot
  per thread. That holds because each group runs on one thread from the factor
  through its stage solves.
- With no context, only solvers whose factors fit in the packed array (such as
  an unpivoted LU) work without global or `_Thread_local` state.

Order for E3, best first ("=" marks a tie):

astra-max = astra-xhigh > astra-high > sol-xhigh > luna-max > sol-high >
sol-max > luna-xhigh > luna-high

Tie-breaks within a rating:

- **astra-max and astra-xhigh** are tied. astra-max has the fullest
  documentation, public CSR getters, and a counting test of the hook.
  astra-xhigh's callbacks receive the whole state, and its tests already
  integrate through a backend with another storage.
- **astra-high** comes after them: its setter is silent, it has no public CSR
  arrays, and no test counts invocations.
- **sol-xhigh before luna-max:** the integrator applies the shift, and the
  context is not shared with the controller.
- **sol-high before sol-max:** sol-high's factor returns a status, it has one
  install site, and there is no generated-offset coupling.
- **luna-xhigh before luna-high:** luna-xhigh has an existing selector and one
  TS1 integrator path.

## Defects found

1. **luna-high, documentation, certain.** `DESIGN.md:112-113` says the
   factorization "can be replaced behind a linear-solver interface". The solver
   path has none: `factor` and `solve_factored` are static
   (`src/solver.c:305-344`) and called directly at `src/solver.c:591,624,854-855,877`.
   The only options structure, `chem_solver_options`, holds tolerances and step
   limits (`include/chemistry.h:630-637`).
2. **sol-max, documentation overstates a check, certain about the code.**
   `DESIGN.md:21` says generated constant indices "are verified against the
   finalized model". The generated loader checks only the count,
   `if (m->nnz != len(indices)) goto fail;` (`tools/configure.py:230`). If the
   Python and C orderings or fills diverged with the same count, the loader
   would accept it. The TS1 test that compares generated and generic kernels
   (`tests/tutorials.c:278-295`) would catch it for the mechanisms it covers.
3. **luna-max, documentation imprecise, fairly sure.** `DESIGN.md:47-48` says
   the solver "factors `alpha * I - J` in place". The default factor copies the
   negative Jacobian into a separate per-thread `lu` buffer and adds
   `alpha * mass_diagonal` there (`src/solver.c:326-332,655-656`), so the
   Jacobian is not overwritten. The wording holds only in the sense that L and
   U share one array. The callback contract (the callback applies the shift,
   one cell per call, an output only nnz long, a context shared by all threads
   and the controller) is not documented.

No defect in the numerical path was found for this exercise. The other items
under Hazards are API traps rather than errors:

- astra-high: the void setter silently ignores an incomplete pair.
- astra-max: `ch_state_set_lu` clears an installed solver.
- sol-xhigh and luna-max: per-member fallback allows a custom factor with the
  built-in solve.
- astra-xhigh: generated literal offsets are not checked against the C plan.
