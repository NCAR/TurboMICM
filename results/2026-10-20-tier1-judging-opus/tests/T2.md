## How the grades were applied

- **Configurations count as assertions.** MICM's Oregonator case runs 17 builder configurations (LU algorithm, vector width, in-place factors). A check that covers fewer of them than the entry's C API can select is P. Variants the C API cannot express (no width parameter, no LU choice for backward Euler) are not held against the entry.
- **Per-step status.** MICM's Oregonator case asserts at every sub-step that the solver state is Converged or ConvergenceExceededMaxSteps, so a step reported as AcceptingUnconvergedIntegration fails it. A check that lets such a step through is weaker (P).
- **Tolerances.** A stricter tolerance does not lower a grade; a looser one is P.
- **Shared functions.** A function registered for several ids is graded by what it checks for this id. MICM's `SurfaceRateConstant.DiffusionCoefficientIsMissing` and case 2 build the same store and expect the same throw, so a check shared by those two ids is not a surrogate.
- **Where the error is raised.** For case 2, an error raised at the C API's own validation point (rate creation, mechanism creation, solver creation, or rate evaluation where the API has no construction step) counts as the error MICM raises at `BuildFrom`.
- **P or S.** P means the same scenario with something weaker or different inputs. S means a check from elsewhere stands in: a different scenario, a generic check shared by many ids, or built-in components in place of the external-model code MICM's case tests.
- **Bundled verdicts.** luna-high prints every PASS line from a fixed list once `bin/test_core` exits 0 (Makefile:48-51; tools/test_cases.py:646-769). luna-xhigh gives every rate-constant and `reaction_rate_store` id the exit code of one `bin/test_rates` run (tools/test_cases.py:74, :113-131, :145-150). For these, the grade describes the check inside that program that corresponds to the case; M would mark a case with no such check (none in this sample).
