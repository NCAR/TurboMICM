# Exercise C: astra-xhigh runs its generator on another mechanism

Entry: branch `tier2/astra/xhigh` (commit 1c9112c), worktree `astra-xhigh/` in this folder, clang with `-O3 -DNDEBUG`, one thread.

**Route:** the benchmark programs themselves. I swapped each converted mechanism in for `configs/ts1.json`, ran `make bench`, and ran `bin/ts1_bench_cpu` and `bin/ts1_bench_specialized`. Nothing in the entry was changed. Both drivers are mechanism-generic: CSV columns are matched by name, and the output lists the mechanism's own species. Only the C symbol names (`ts1_mechanism`, `ts1_specialized`) are fixed, and the Makefile passes those to the generators. **All three mechanisms pass every comparison at 4 and at 64 cells.**

## Did the specialized program run the generated kernels? Yes, at 4 and at 64 cells

**Code path.** `src/bench.c`, compiled with `-DCHEM_SPECIALIZED` into `bin/ts1_bench_specialized`, sets `generic=1` only when given `--generic`. Otherwise every group, in the warm-up and in every timed step, calls `ts1_specialized.rates(&states[g])` and `ts1_specialized.solve(&states[g],dt)`, with no test of the cell or group count. `ts1_specialized.solve` is the generated `specialized_solve`, built from `tools/ros3.c.in` by `tools/tiled.py`'s `transform_solver`. It does three things:
- pads any cell count to a multiple of the 4-cell tile, `padded=(active+3)/4*4`; dummy lanes get zero rates and are left out of the error norm;
- packs `y` and the rates into a private tiled workspace;
- calls only the generated `packed_forcing/jacobian/add_alpha/factor/linear` kernels, which call the `tile_*` kernels.

The generated file contains no call into the generic library: no `chem_*()` call at all. 4 cells make one group of 4, which is one full tile; 64 cells make two groups of 32, which are 8 tiles each. Neither case needs padding, and there is no fallback.

**At run time.** I also ran the same binary with `--generic`, the program's own generic path (`chem_calculate_rates` and `chem_ros_solve`, with the table evaluator):
- **CB5 and CB5 without emissions:** the default output differs bit for bit from the `--generic` output at both 4 and 64 cells (largest differences 4.38e-15 and 3.61e-15 at 4 cells, 2.56e-14 and 2.18e-14 at 64). The default run is also 3.7 to 6.2 times faster. The binary holds 53 `tile_*` functions, the kernel parts called through volatile pointers.
- **Chapman:** the generated solver reproduces the generic arithmetic exactly, so the two outputs are bit-for-bit identical and only time tells the paths apart:
  - 0.066 against 0.263 ms at 4 cells;
  - 0.637 against 2.721 ms at 64 cells;
  - 210 to 215 against 856 to 885 ms over three alternating runs of 64 cells x 20,000 steps.

  The tile functions are inlined at this size, so there are no `tile_*` symbols, but `specialized_solve` and `calculate_rates` are in the symbol table.
- **Call stacks:** I tried to capture them with macOS `sample`. It hung, apparently for lack of a developer-tools permission, so I stopped the job and restored the configuration.

## What it took

**The entry's format.** The format is the CAMP-style JSON that `configs/ts1.json` uses, read by `tools/configure.py`. Every feature of the canonical mechanisms has a direct TS1 counterpart, so the converter (119 lines, standard library only) only maps names. It does not hand-edit anything:

| Canonical | astra-xhigh configuration, as in TS1 |
|---|---|
| species, `third_body: true` | `{"name", "type": "CHEM_SPEC", "parameterization": "air density"}`, as TS1's M |
| other species, `initial.concentrations` | `CHEM_SPEC` with `"initial concentration [mol m-3]"`; 0.0 when none is given, as MICM's InitState and cells.csv do |
| M in reactants and products | kept where the canonical file has it, as TS1 does |
| ARRHENIUS A–E, TROE k0_*, kinf_*, Fc, N | the same keys |
| USER_DEFINED `label`, `scaling_factor` | `"MUSICA name"`, `"scaling factor"` |
| emission (no reactants) | USER_DEFINED with `"reactants": []`, which the reader accepts; it also has an EMISSION type, unused here |
| products `[name, yield]` | `{"species", "yield"}`; negative yields and repeated reactants pass through unchanged |
| every reaction | `"concentration units": "mol m-3"`, as on all of TS1's |
| `initial.temperature`, `initial.pressure` | `"initial conditions"` |
| `initial.parameters` | `"initial rate parameters"`; the 5 labels without a value are left out (zero at start, set by cells.csv) |

I checked the converted files by reading them back through the entry's own `configure.read`: species order, reactions, terms, and parameters equal the canonical file exactly.

**Things to watch in the format:**
- **Units:** `"concentration units"` defaults to molecule cm-3, which would rescale A, k0_A, and kinf_A by powers of 6.022e17. Leaving it out would give wrong rates without any error.
- **Rate-parameter keys:** an `"initial rate parameters"` key that names no reaction's label makes `chem_state_create` fail, because `chem_state_set_custom` returns an error.
- **The third body:** the generic path multiplies the rate constant by the air density for each non-variable reactant (`chem_calculate_rates` in `src/state.c`). The specialized code emits `k *= M` (`tools/specialize_rates.py`). Products listing M are ignored. The air density comes from T and p by the ideal gas law, as in MICM, so the canonical file's `environment.air_density` is not needed.

**The generator.** It is fully mechanism-generic, as SPECIALIZATION.md claims:
- It is fast: 0.07 s for CB5 and 0.56 s for TS1.
- Its output is deterministic: 5 repeats gave byte-identical output.
- It compiles warning-free.
- The generated C scales with the mechanism: about 25,500 lines (0.85 MB) for CB5 against 75,000 lines (2.6 MB) for TS1.
- Compile time dominates the build: 7.5 s for CB5 and about 69 s for TS1, against generators that run in under a second.

**Surprises:**
1. `make env` is not offline for this entry. It creates `.conda` with `conda env create` from conda-forge and a private package cache (`.conda-pkgs`), so a fresh worktree must download Python, PyYAML, NumPy, and their dependencies; the review's earlier exercise log shows the downloads. To keep to the no-network rule, I copied this entry's own environment from its verification worktree. It was made by the same `make env` from the identical `environment.yml`. I then touched `conda-meta/history` so that `make env` had nothing to do.
2. The Makefile names `configs/ts1.json` directly in its rules, not through a variable, so another mechanism needs the file swap.
3. The entry's own `tools/translate_ts1.py`, which reads MICM's C++ header, accepts only TS1: it requires 210 species and 547 reactions. It could not have converted the MICM headers of these mechanisms.
